# 1. DDL , DML, DCL

### DDL ( Data Definition Language )

> 데이터 정의어 : 데이터 생성, 수정, 삭제 등 데이터 전체 골격 결정
> 

→ DB 관리자나 설계자가 사용

- `create` : DB/테이블 생성
- `alter` : 테이블 수정
- `drop` : DB/테이블 삭제
- `truncate` : 테이블 초기화

### DML ( Data Manipulation Language )

> 데이터 조작어 : 정의된 DB에 입력된 레코드 조회, 수정, 삭제
> 

→ DB 사용자가 저장된 데이터를 실질적으로 처리하는데 사용

→ DB 사용자와 DB 관리 시스템 간 인터페이스 제공

- `select` : 데이터 조회
- `insert` : 데이터 삽입
- `update` : 데이터 수정
- `delete` : 데이터 삭제

### DCL ( Data Control Language )

> 데이터 제어어 : DB에 접근하거나 객체에 권한 부여
> 
- `grant` : 특정 DB 사용자에게 특정 작업에 대한 수행 권한을 부여
- `revoke` : 특정 DB 사용자에게 특정 작업에 대한 수행 권한을 **박탈, 회수**

### TCL ( Transaction Control Language )

> 트랜젝션 제어어 : DML에 의해 조작된 결과를 트랜잭션별로 제어
> 
- `commit` : 트랜잭션의 작업을 저장
- `rollback` : 트랜잭션의 작업을 **취소, 원래대로 복구**
- `savepoint` : Commit 전에 특정 시점까지만 반영하거나 Rollback하겠다는 명령어

# 2. 힌트 ( Hint )

<aside>

**쿼리 실행 계획 ( execution plan )**

- DB에서 query를 수행할 때, 어떤 방식으로 데이터를 조회 / 처리할지 계획
- DBMS에 의해 쿼리 옵티마이저가 최적의 방법을 선택

**쿼리 옵티마이저 ( query optimizer )**

- 쿼리를 처리할 때 가장 효율적인 방법을 선택하기 위해 여러 정보를 고려
    - ex ) 테이블의 크기, 인덱스의 유무, 통계정보, 서버 자원 상황…
- 여러 정보를 고려하여 → 여러 실행 계획을 구상
- DB의 성능과 관련이 깊음
</aside>

> **💡 그래서 힌트란 ?**
> 
> 
> 쿼리 옵티마이저가 자동으로 생성한 실행계획이 최적의 방법이 아니라고 판단될때
> 
> →  Hint를 제공하여 쿼리 옵티마이저에게 직접 최적의 실행경로를 작성
> 
> ex ) 인덱스 사용 지시, 테이블 조인 순서 제안 …
> 

```sql
SELECT /*+ HINT_NAME */ 컬럼명 FROM 테이블명 WHERE 조건;
```

‼️ /*+*/로 둘러싸여 있어 주석처럼 생겼지만 힌트로 특정한 것

# 3. 인덱스

> DB 테이블의 검색 속도를 향상시키기 위한 자료구조
> 
> 
> : 책의 모든 페이지를 찾아보기 어려울때, 책의 맨 앞에 표시된 색인과 같음
> 
- 대용량 데이터 조회 → 인덱스 활용시 → `SELECT`, `UPDATE`, `DELETE` 성능 향상
    - 해당 대상을 조회해야 작업이 가능하기 때문
    - 인덱스 설정되지 않은 경우 Full Scan 수행하기 때문에 속도 저하

📌 하지만, 인덱스 생성 시 무조건 빠른 검색이 이루어지는 것 ❌

- 인덱스 생성 시 → 인덱스를 위한 디스크 공간이 필요
- 인덱스 가진 테이블에 DML 작업 시 더 많은 자원 필요

✅ 따라서 테이블의 의도를 정확하게 파악 후 상황에 맞게 적절한 칼럼으로 구성해야함

# 4. 인덱스의 자료구조

### B Tree

> 균형 잡힌 탐색 트리
> 
> 
> 모든 leaf 노드의 깊이가 동일한 트리구조
> 
- 내부 노드와 leaf 노드 모두에 데이터를 가지고 있음
- 데이터가 중간 노드에도 있으므로 삽입/삭제가 복잡함

### Clustered 인덱스

> 데이터가 테이블에 물리적으로 저장되는 순서를 정의하는 인덱스
> 

**: 페이지를 알고 있기 때문에 바로 그 페이지를 펼 수 있는 구조**

<img width="531" height="242" alt="스크린샷 2026-02-20 오후 6 42 43" src="https://github.com/user-attachments/assets/64cc3ded-7278-4952-a836-9c08e3611388" />

- 행 데이터를 해당 열로 정렬하여 loot 페이지 생성
    - leaf 페이지의 주소를 Loot에 저장
    - leaf 페이지는 실제 데이터 페이지
- 생성 및 정렬
    - 테이블의 데이터가 인덱스 키 값에 따라 물리적 정렬
    - 한 테이블에 하나의 클러스터형 인덱스만 생성가능
- 성능
    - 데이터 페이지 자체가 인덱스의 일부 → 데이터에 직접 접근하여 검색 속도 빠름
- 기본 키
    - 대부분 DB 시스템에서 PK를 설정하면 자동으로 클러스터형 인덱스가 생성
        
        ( id가 PK인 경우 테이블은 id순서로 정렬 )
        

### Non-Clustered 인덱스

> 정렬된 별도의 인덱스 페이지로 저장되고 관리하는 구조
> 

: 목차에서 찾고자 하는 내용의 페이지를 찾고 그 페이지로 이동하는 구조

<img width="462" height="306" alt="스크린샷 2026-02-20 오후 6 43 00" src="https://github.com/user-attachments/assets/da00f778-a5b0-4e70-b1a2-52b5f9ff0b97" />

- 데이터 페이지를 건드리지 않고 별도의 장소에 인덱스 페이지 생성
    - 원본은 정렬되지 않고, 인덱스 페이지만 정렬
- 생성 및 정렬
    - 테이블당 약 240개 생성 가능
    - 원본 데이터 페이지는 정렬되지 않음
- 성능
    - 데이터 페이지를 둔 상태로 별도의 인덱스 페이지 생성 → 용량 차지
        - 인덱스 페이지의 leaf에 인덱스로 구성한 열을 정렬한 후 위치 포인터 생성
    - 검색 속도는 느리지만 입력/수정/삭제는 빠름
        - cluster의 경우 입력, 삭제 등등 수행할때 페이지 분할이 일어남
        - non cluster의 경우 데이터 페이지를 건드리지 않으므로 분할이 일어나지 않음
            
            → 이러한 면에서 검색을 제외한 부분에서 성능이 빠름
            

| **구분** | **Clustered** | **Non-Clustered** |
| --- | --- | --- |
| 물리적 저장 | 데이터 자체 정렬 | 데이터 정렬 X |
| 인덱스 개수 | 하나만 생성 | 여러개 생성 |
| 성능 | 조회 성능 빠름 | 입력/수정/삭제 빠름 |
| 주로 사용되는 경우 | PK | Secondary Key |

### 멀티 인덱스

> 여러 열을 결합하여 하나의 인덱스로 만드는 것
> 
- 데이터 조회 성능 향상
    - 데이터 조회 시 , 빈번하게 같이 조회되는 컬럼들 대상으로 성능 향상

**⁉️ 그냥 두개 인덱스로 조회하면 되지 않을까? 왜 써야할까?**

❌ 각 컬럼에 따로 인덱스가 걸려있는 경우

```sql
INDEX idx_name (name)
INDEX idx_age (age)
```

- 어떤 인덱스를 먼저 사용하는 것이 빠른지 옵티마이저가 판단 이후, 순서대로 인덱스 적용
    
    ex )  name=‘철수’ → 10명 / age=30 → 1000명 ⇒ name 인덱스가 더 효율적
    
    따라서 name 인덱스로 필터링 이후 그 결과에서 age 조건을 다시 검사
    

**✅ 멀티 인덱스의 경우**

```sql
INDEX idx_name_age (name, age)
```

ex ) B + Tree 구조이므로

```sql
name
  └── age
```

이미 name 기준으로 정렬, 그 내부에서 age 기준으로 정렬

따라서 name=‘철수’로 트리 탐색 이후 그 범위 안에서 바로 age = 30을 찾음

### 커버링 인덱스

> 쿼리를 충족시키기 위한 모든 데이터를 가지고 있는 인덱스
> 
> 
> 테이블 자체에 접근할 필요 없이 모든 필요한 데이터를 찾을 수 있음
> 
- 인덱스에서 충족하는 데이터를 갖고 있어 디스크 I/O 줄임
- 테이블 락을 줄임으로써 DB의 전반적인 부하 감소, 성능 향상
    
    ex ) 인덱스 내에 name, age가 이미 있으므로 테이블을 다시 읽을 필요가 없음
    
    ```sql
    // 예시
    SELECT name, age
    FROM users
    WHERE name = '철수';
    
    // 예시의 커버링 인덱스 
    INDEX idx_name_age (name, age)
    ```
    

# 5. 정규화, 반정규화

### 정규화

> 이상 문제를 해결하기 위해 속성들끼리의 관계를 분석하여 여러개의 릴레이션으로 분해
> 
- **이상**
    - 삽입 이상 : 원하지 않은 값들도 함께 삽입
    - 삭제 이상 : 상관없는 값들도 함께 삭제
    - 갱신 이상 : 일부 튜플들의 정보만 갱신되어 정보에 모순 발생
- **함수적 종속**
    
    : X의 값에 따라 Y값이 결정될 때 ( X -> Y ),  Y는 X에 대해 함수적 종속
    
    - 부분함수종속 → 제거한 것이 제**2**정규형
        - 기본키가 단일키일 경우 부분함수종속은 일어날 수 없음
        - 기본키가 복합키일 경우 X1, X2 중 하나만으로도 Y의 값을 결정할 경우
    - 완전함수종속 → 만족한 것이 제**2**정규형
        - 기본키가 단일키일 경우 , X -> Y 일 경우
        - 기본키가 복합키일 경우, {X1,X2} -> Y일 경우
    - 이행적함수종속 → 제거한 것이 제**3**정규형
        - X -> Y인데, Y -> Z, 결국 X -> Z인 것을 알 수 있는 경우

### 반정규화

> 정규화의 일부를 되돌려, 데이터의 중복을 의도적으로 허용하고, 데이터베이스의 성능을 향상시키는 과정
> 
- 데이터 무결성 : 데이터의 정확성, 일관성, 신뢰성을 유지
    
    → 반정규화 시 데이터 중복으로 인해 저하될 수 있으므로 신중해야함
    
    - 도메인 무결성
        
        : 필드의 값이 정의된 유효한 값의 집합에 속해야 한다는 것을 보장
        
    - 개체 무결성
        
        : 각 행이 고유함을 보장하며, 주 키 값이 유일하고, null이 아니어야 함
        
    - 참조 무결성
        
        : 외래 키 값이 참조하는 테이블의 기본 키 값과 일치해야 하며, 관계의 일관성을 유지해야 함
        

# 6. Connection Pool

> 
> 
> 
> DB 연결(Connection)을 미리 여러 개 생성해두고, 필요할 때 빌려 쓰고 다시 반납하는 방식
> 

❌ Connection 객체 생성 과정 매우 비효율적

→ DB 연결할 때마다 Connection 객체를 새로 만드는 것은 비용 낭비 + 비효율

```sql
// Connection 객체 생성 과정
- 애플리케이션에서 DB 드라이버를 통해 커넥션을 조회한다.
- DB 드라이버는 DB와 TCP/IP 커넥션을 연결한다. (3 way handshake와 같은 네트워크 연결 동작 발생)
- DB 드라이버는 TCP/IP 커넥션이 연결되면 아이디와 패스워드, 기타 부가 정보를 DB에 전달한다.
- DB는 아이디, 패스워드를 통해 내부 인증을 거친 후 내부에 DB를 생성한다.
- DB는 커넥션 생성이 완료되었다는 응답을 보낸다.
- DB 드라이버는 커넥션 객체를 생성해서 클라이언트에 반환한다.
```

**✅ Connection Pool 등장**

애플리케이션 로딩 시점에 Connection 객체를 미리 생성 

→ DB에 연결이 필요할 경우 미리 준비된 Connection 객체를 이용하여 성능 향상

- 동작구조

1. 애플리케이션을 시작하는 시점에 커넥션 풀은 필요한 만큼 커넥션을 미리 생성
2. 기본값으로 10개 생성 ( 서비스의 스펙에 따라 생성되는 Connection 객체의 개수는 다름 )
3. 커넥션 풀의 Connection 객체는 TCP로 DB와 연결되어 있는 상태 → 즉시 SQL을 DB에 전달할 수 있음
4. 즉, DB 드라이버를 통해 새로운 커넥션을 획득하는 것이 아닌 이미 생성되어 있는 커넥션을 참조하여 사용
5. 커넥션 풀에 있는 커넥션을 요청하면 커넥션 풀은 자신이 가지고 있는 커넥션 객체 중 하나를 반환

→ DB 드라이버를 통해 커넥션을 조회, 연결, 인증, SQL을 실행하는 시간 등 커넥션 객체를 생성하기 위한 과정을 생략할 수 있음

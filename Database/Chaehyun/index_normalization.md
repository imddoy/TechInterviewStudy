## DDL, DML, DCL

### DDL

- Data Definition Language
- 데이터 정의어
- 테이블이나 인덱스 같은 DB 구조 자체를 생성, 변경, 삭제
- CREATE, ALTER, DROP, TRUNCATE
- 실행 즉시 Auto-commit 되는 경우가 많아 롤백이 어려움

### DML

- Data Manipulation Language
- 데이터 조작어
- 테이블 안의 실제 데이터를 다룸
- 조회, 삽입, 수정, 삭제
- SELECT, INSERT, UPDATE, DELETE
- 트랜잭션의 주요 대상
- 롤백/커밋 가능

### DCL

- Data Control Language
- 데이터 제어어
- DB에 접근하거나 객체를 사용할 수 있는 권한 부여/회수
- GRANT, REVOKE
- 보안 및 사용자 관리 목적

### TCL

- Transaction Control Language
- 트랜잭션 제어어
- DML로 조작한 결과를 논리적인 작업 단위로 제어
- COMMIT, ROLLBACK, SAVEPOINT
- DCL에서 분리해서 부르기도 함

## Hint

- DB의 옵티마이저가 항상 최적의 실행 계획을 짜는 것은 아니기 때문에, 개발자가 직접 “이 방식으로 쿼리를 실행해!”라고 제시하는것
- 주석 기호 내에 `+` 를 붙여 사용
    
    `SELECT /*+ INDEX(emp idx_emp_name) */ name FROM emp;`
    
- 옵티마이저가 엉뚱한 인덱스를 타서 쿼리가 느려질 때 사용
    - 강제로 특정 인덱스를 태우거나, 조인 순서(Nested Loop 등)를 지정하고 싶을 때
- 데이터의 분포나 양이 크게 변했는데 힌트를 그대로 방치하면 오히려 성능이 심각하게 저하될 수 있으므로 남용하지 않기

## Index

- 데이터 검색 속도를 비약적으로 높여주지만, 데이터 변경(INSERT, UPDATE, DELETE) 시 인덱스도 함께 업데이트해야 하므로 쓰기 성능은 떨어지고 추가 저장 공간이 필요

### Cluster 인덱스와 Non-Cluster 인덱스

- Cluster 인덱스 (클러스터형 인덱스)
    - 물리적 정렬: 테이블의 실제 데이터 자체가 이 인덱스 기준으로 정렬되어 저장
    - 개수 제한: 테이블당 단 1개만 생성 가능
        - 주로 Primary Key가 자동으로 클러스터 인덱스가 됨
    - 특징: 리프 노드가 곧 실제 데이터 행(Row) ⇒ 검색 속도가 매우 빠름

### 멀티 인덱스 (복합 인덱스)

- 두 개 이상의 컬럼을 합쳐서 하나의 인덱스로 만듦
- 순서가 생명 : (A, B)로 만든 인덱스와 (B, A)로 만든 인덱스는 다름
    
    ⇒ 전화번호부를 ‘성, 이름’순으로 정렬한 것과 ‘이름, 성’ 순으로 정렬한 것의 차이
    
    - **컬럼의 순서는 어떻게 정해야 할까요?**
        1. 카디널리티(Cardinality, 분포도)가 높은 컬럼을 앞에 둠
            - 카디널리티가 높다는 것은 중복되는 값이 적고 고유한 값이 많다는 뜻
                
                ex) 주민등록번호 > 이름 > 성별
                
            - 데이터를 가장 획기적으로 걸러낼 수 있는 조건이 앞쪽에 와야 탐색해야 할 전체 데이터 양이 빠르게 줄어듦
        2. 동등 비교(=)를 하는 컬럼을 범위의 검색(<, >, BETWEEN) 컬럼보다 앞에 둠
            - 인덱스 탐색 시, 범위 검색 조건이 앞쪽에 등장하면 그 뒤에 있는 컬럼들은 인덱스를 제대로 타지 못하고 풀 스캔에 가깝게 동작하는 경우가 많음
            - `WHERE 성별 = ‘F’ AND 가입일 ≥ ‘2024-01-01’`
                
                ⇒ 인덱스를 (성별, 가입일) 순으로 구성해야 성능이 최적화
                
- 조회 쿼리에서 왼쪽 컬럼부터 조건에 사용되어야 인덱스를 제대로 탈 수 있음

### 커버링 인덱스 (Covering Index)

- 쿼리를 충족시키는 데 필요한 모든 데이터를 인덱스 자체가 가지고 있는 경우를 말함
- (이름, 나이)로 인덱스가 걸려있을 때, `SELECT 나이 FROM 테이블 WHERE 이름 = ‘김채현’` 쿼리를 날리면, 인덱스만 뒤져봐도 나이를 알 수 있음
- 장점: 실제 데이터 블록(디스크)까지 찾아갈 필요가 없으므로 성능이 극단적으로 좋아짐

## B+Tree

- 대부분의 RDBMS가 인덱스를 저장하기 위해 사용하는 자료구조
- B-Tree 계열의 Balanced Tree 종류 중 하나
- MySQL의 InnoDB 스토리지 엔진은 주로 B+Tree 사용
- 데이터베이스 인덱스와 파일 시스템 사용에 더 적합할 수 있도록 만들어짐
- 왜 하필 B-Tree 계열인가요?
    - DB는 데이터를 디스크에서 블록 단위로 퍼옴
    - 이진 트리(Binary Tree)는 한 노드에 자식이 2개뿐이라 깊이가 너무 깊어져 디스크 I/O가 많이 발생
    - B-Tree는 하나의 노드에 여러 개의 데이터를 담아 넓고 얕은 모양(균형 트리)를 유지하여 O(log N)의 일관된 탐색 속도를 보장함
- B+Tree의 특징
    - **같은 레벨의 모든 키값들이 정렬**되어있고, **같은 레벨의 Sibling node는 연결리스트 형태**로 이어져 있음
        - 실제 데이터 또는 포인터는 무조건 가장 아래쪽의 리프 노드에만 있음
        - 리프 노드들끼리는 연결 리스트(Linked List)로 이어져 있음
    - 인덱스 노드
        - 리프 노드가 아닌 자료
        - 다음 노드를 가리킬 수 있는 포인터 주소가 존재
    - 데이터 노드
        - 리프 노드 자료
        - 데이터가 존재
    
    ⇒ 키 값은 중복될 수 있고(인덱스 노드와 데이터 노드에서 동시에 등장 가능), 데이터 검색을 위해서는 반드시 리프 노드까지 내려가야 함
    
    - 장점: `WHERE age BETWEEN 20 AND 30` 같은 범위 검색을 할 때, 리프 노드에 도달한 뒤 옆으로 쓱 훑기만 하면 되기 때문에 성능이 아주 좋음

- **B-Tree 인덱스와 Hash 인덱스의 차이점?**
    - 왜 대부분의 상용 DB(MySQL, Oracle 등)가 기본 인덱스로 속도가 가장 빠른 Hash를 두고 굳이 B-Tree(B+Tree)를 사용할까?
    - Hash 인덱스
        - 특징: 해시 함수를 거쳐 데이터의 물리적 위치를 바로 찾기 때문에 탐색 속도가 O(1)
        - 단점:
            - 오직 정확히 일치하는 값을 찾을 때만 사용 가능
            - 부등호나 문자열 포함 같은 범위 검색이 아예 불가능
            - 해시 함수를 통과한 결과값은 원래 데이터의 대소 관계를 유지하지 않기 때문
    - B-Tree (B+Tree) 인덱스
        - 특징: 탐색속도는 O(log N)으로 Hash보다는 약간 느리지만, 데이터가 항상 **정렬된 상태**를 유지
        - 장점:
            - `WHERE age ≥ 20` 같은 범위 스캔, `ORDER BY`를 통한 정렬 등에 완벽하게 대응 가능
            - 실제 서비스에서는 단순 일치 검색보다 범위 검색이나 정렬이 압도적으로 많이 쓰이므로 B-Tree 구조가 표준
            

> **조회 성능을 위해 모든 컬럼에 인덱스를 걸어버리면 어떤 문제가 발생할까요?**
> 
- SELECT 속도는 일시적으로 빨라질 수 있지만, 치명적인 쓰기 성능 저하와 자원 낭비가 발생
- 데이터가 추가, 수정, 삭제(INSERT, UPDATE, DELETE)될 때마다 테이블에 걸려있는 모든 인덱스의 B-Tree 구조를 재정렬하고 갱신해야 하므로 심각한 병목 현상 발생
- 수많은 인덱스가 디스크 공간을 과도하게 차지하게 되고, DB 옵티마이저가 실행 계획을 짤 때 선택지가 너무 많아져 오히려 비효율적인 인덱스를 타게 될 위험이 높아짐

⇒ 카디널리티가 높고, WHERE 절이나 JOIN 조건에 자주 사용되는 핵심 컬럼에만 선별적으로 인덱스를 생성해야 함!!

- Page Split (페이지 분할)
    - 데이터가 중간에 삽입/수정되면 B-Tree 노드(페이지)의 공간이 부족해질 수 있음
        
        ⇒ DB는 공간을 확보하기 위해 노드를 두 개로 쪼개는 페이지 분할을 하는데
        
        ⇒ 엄청난 디스크 I/O가 발생하며 쓰기 성능 저하
        
        ⇒ 모든 컬럼에 인덱스가 있다면 이 문제가 모든 인덱스에서 동시다발적으로 일어남
        
- 송금 서비스나 글로벌 라이프스타일 플랫폼처럼 유저의 활발한 활동(쓰기 작업)이 빈번한 시스템에서 무작정 인덱스를 늘리는 것은 시스템 전체를 멈추게 할 수 있음


> **수천만 건의 라이브 테이블에 인덱스를 새로 추가하면 어떤 일이 생기고, 어떻게 작업해야 할까요?**
> 
- 일반적인 DDL(CREATE INDEX) 방식으로 인덱스를 추가하면 테이블 전체에 Table Lock이 걸리게 됨
    - 락이 걸리는 이유
        - 인덱스를 만들려면 현재 테이블에 있는 데이터를 빠짐없이 읽어서 정렬해야 함
            
            ⇒ 정렬하고 있는 도중에 누군가 데이터를 바꾸거나 추가하면 인덱스가 꼬여버림
            
            ⇒ 과거의 DB들은 아무도 데이터를 못 건드리게 락
            
- 수천만 건의 데이터를 정렬해 **B-Tree를 구성하는 긴 시간 동안 해당 테이블에 대한 모든 쓰기(INSERT/UPDATE/DELETE) 요청이 대기 상태**에 빠지며, 결국 **타임아웃으로 인한 대규모 서비스 장애**로 이어짐
- MySQL의 **Online DDL**(ALGORITHM=INPLACE, LOCK=NONE) 기능을 사용하며 인덱스 생성 중에도 DML 작업을 허용하도록 해야 함
    - Online DDL
        - 최신 RDBMS는 락을 걸지 않고 인덱스를 만드는 동안 변경되는 데이터들을 임시 로그 공간에 따로 적어둠
        - 인덱스 뼈대를 다 만든 다음, 임시 공간에 적어둔 변경 사항들을 마지막에 한 번에 반영하는 방식으로 무중단 인덱스 생성을 지원
- 인덱스 생성 자체로도 DB의 CPU와 메모리 자원을 크게 소모하므로 반드시 트래픽이 가장 적은 새벽 시간대에 작업 수행
- 서드파티 툴
    - 만약 구형 DB이거나 Online DDL로도 부하가 감당 안될 때는 pt-online-schema-change 같은 툴 사용
    - 빈 껍데기 복사본 테이블을 만들고 거기에 인덱스를 건 다음, 원본 테이블의 데이터를 백그라운드에서 복사해 오고 마지막에 테이블 이름을 swap

## 정규화와 반정규화

### 정규화

- 목적: 데이터 중복을 최소화하고 이상 현상을 방지
- 과정: 덩치가 큰 테이블을 특정 규칙(함수적 종속성 등)에 따라 잘게 쪼개짐
    - 1정규형, 2정규형, 3정규형, BCNF 등..
- 결과: 무결성이 보장되고 업데이트/삽입 시 오류가 적어지지만, 데이터를 조회할 때 JOIN이 너무 많이 발생하여 읽기 성능이 떨어질 수 있음

### 반정규화

- 목적: 정규화로 인해 너무 쪼개진 테이블 때문에 읽기 성능(SELECT)이 저하되는 것을 막기 위해 의도적으로 정규화 원칙을 위배
- 과정: 테이블을 합치거나, 중복 컬럼을 추가하거나, 요약 테이블 생성
- 결과: 조회 속도는 빨라지지만, 데이터의 일관성을 유지하기 위해 애플리케이션 로직이 복잡해지고 쓰기 성능이 약간 떨어짐

## 커넥션 풀 (Connection Pool)

- 배경: 애플리케이션이 DB와 통신하려면 매번 네트워크 연결(TCP 3-way handshake)을 맺고 인증을 거쳐야 하는데, 이 과정이 매우 무겁고 느림
- 개념: 애플리케이션이 켜질 때, DB와의 연결을 미리 여러개 맺어두고 Pool에 보관
- 동작 방식
    1. 클라이언트 요청이 오면, 미리 만들어둔 커넥션 하나를 빌려줌
    2. 작업이 끝나면 커넥션을 끊지 않고 다시 Pool에 반납
- 효과: 연결을 생성/종료하는 오버헤드가 사라져 응답 속도가 대폭 향상되고, DB에 가해지는 부하를 제어할 수 있음 ⇒ Java 기반 백엔드에서는 HikariCP가 사실상 표준

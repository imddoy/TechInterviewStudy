## 관계형 DB vs NoSQL

### RDBMS (MySQL, Oracle, PostgreSQL)

- 엄경한 스키마를 가지고 있으며, 테이블 간의 관계(Foreign Key)를 맺음
- ACID(원자성, 일관성, 고립성, 지속성)을 철저히 보장
- 데이터의 정합성이 완벽히 보장
- 트래픽이 늘어났을 때 서버를 여러 대로 늘리는 Scale-out이 구조적으로 어려움
- 결제, 송금, 예약 등 데이터의 정확성이 생명인 시스템에서 사용

### NoSQL (MongoDB, Redis, Cassandra)

- 스키마가 없거나 유연하며, 관계를 정의하지 않음
- 데이터 정합성보다는 가용성과 확장성에 초점
- 서버를 늘려서 용량과 성능을 무한대로 확장하기 쉽고 읽기/쓰기 속도가 빠름
- 데이터의 일관성이 즉각적으로 보장되지 않을 수 있음 (Eventual Consistency)
- 실시간 채팅 로그, 장바구니, 세션 데이터, 대규모 로그 수집 등 정합성보다 속도와 확장이 중요한 시스템

## 클러스터링(Clustering) vs 레플리케이션(Replication)

DB 서버가 1대일 때, 이 서버가 죽으면 서비스 전체가 멈추는 단일 장애점(SPOF) 문제 발생

⇒ 해결하기 위해서는 물리적/논리적 복제 방법 필요

### Replication

<img width="611" height="611" alt="image" src="https://github.com/user-attachments/assets/3e97c290-4625-4afb-a2c7-d7e2e61e409f" />


- **Master DB**와 하나 이상의 **Slave DB**로 나눔
- Master에 쓰기(`INSERT`/`UPDATE`)가 발생하면 그 로그를 Slave로 보내어 데이터를 똑같이 복사(동기화)
    1. 클라이언트가 Master DB에 데이터를 쓰면, Master는 변경 내역을 **Binlog(바이너리 로그)에 기록**
    2. Slave DB가 이 Binlog를 가져와서 자신의 **Relay Log**에 적음
    3. Slave DB가 Relay Log를 순차적으로 실행하여 Master와 동일한 상태를 맞춤
- 실제 서비스 트래픽의 80~90%는 조회(SELECT) ⇒ Master는 쓰기 전용으로 두고, Slave들을 읽기 전용으로 두어 부하를 분산
- 비동기 복제로 인해 Master에 쓰자마자 Slave에서 읽었을 때 옛날 데이터가 조회되는 **Replication Lag(복제 지연)** 현상이 발생할 수 있음
    
    ⇒ 결제 직후 잔액 조회처럼 절대 지연이 발생하면 안되는 핵심 로직은 강제로 **Master DB를 바라보게 라우팅**하는 전략 사용
    
    - 코드레벨에서의 라우팅
        - 일반 쓰기/수정 작업 (Master로 라우팅)
            - 코드에 `@Transactiona`l을 기본값으로 붙이면, SpringBoot가 데이터 변경이 일어날 수 있는 중요한 작업임을 인지해서 MasterDB 커넥션을 빌려와서 쿼리를 날림
        - 단순 조회 작업 (Slave로 라우팅)
            - 코드에 `@Transactional(readOnly=true)` 라고 명시해주면, 프레임워크가 일기 전용이기 때문에 Slave DB 커넥션으로 알아서 쿼리를 보냄
    - 미들웨어/프록시 레벨에서의 라우팅
        - ProxySQL, MySQL Router, AWS Aurora의 기본 엔드포인트
        - 쿼리를 프록시 서버로 던지면, 프록시가 날아온 SQL 문장을 보고 SELECT로 시작하면 Slave, INSERT, UPDATE, DELETE로 시작하면 Master로 알아서 분류해서 보냄
        - 개발자가 코드에 일일이 라우팅 설정을 하지 않아도 돼서 편리함
    
    ⇒ DB 자체의 설정으로 지연 줄이기
    
    - 비동기 복제(기본값): Master는 Slave가 로그를 잘 받았는지 확인 안하고 바로 커밋
        - 속도 빠름, 데이터 유실 위험 있음
    - 반동기 복제 (Semi-Synchronous Replication): Master가 커밋하기 전에, 최소 1대의 Slave가 릴레이 로그에 데이터를 무사히 기록했다는 응답(ACK)을 받을 때까지 대기
        - 속도는 살짝 느려지지만 결제/금융 데이터처럼 정합성이 중요할 때 데이터 유실(SPOF)을 막음
    
    <img width="1132" height="1252" alt="image" src="https://github.com/user-attachments/assets/b9b4969f-acbd-4a92-aa92-d59a48d8238d" />

    

> **레플리케이션 환경에서 유저가 회원가입을 완료하자마자, 바로 ‘내 정보 보기’ 페이지로 이동했습니다. 그런데 ‘존재하지 않는 유저’라고 에러가 떴습니다. 원인이 무엇이고 어떻게 해결할까요?**
> 
- 레플리케이션의 비동기 복제 방식 때문에 발생하는 ‘Replication Lag(복제 지연)’ 현상
    
    ⇒ Master에 회원가입 정보가 저장된 후, 그 데이터가 Slave로 복사되기까지 미세한 시간 차이가 존재
    
    ⇒ FE에서 회원가입 직후 곧바로 Slave DB로 조회 요청이 들어가면, 아직 복사되지 않은 옛날 데이터를 읽게 되어 발생
    
- 결제 직후의 잔액 조회나, 회원가입 직후의 정보 조회처럼 ‘절대적인 최신 데이터(강한 일관성)’가 필요한 요청은, Slave가 아닌 Master DB로 직접 읽기 요청(SELECT)을 보내도록 애플리케이션(BE)에서 라우팅 처리

⇒ FE에서 낙관적 업데이트나 지연 호출하여 대처 가능

### Clustering

- 여러 대의 DB 서버를 묶어서 마치 하나의 시스템처럼 동작하게 만듦
- Active-Active
    - 모든 DB 서버가 살아서 일을 함
    - CPU/메모리 자원을 10% 활용할 수 있어 성능이 좋음
    - 여러 서버가 하나의 스토리지에 동시에 데이터를 쓰려고 하면 충돌
        
        ⇒ 한쪽이 쓸 때 다른 쪽은 대기해야 하는 **병목 현상(Lock 경합)이 발생해 오히려 성능이 떨어질 수 있음**
        
- **Active-Standby**
    - 한 대만 일을 하고, 다른 한 대는 대기
    - Active 서버가 죽으면, 대기하던 Standby 서버가 즉시 Active로 전환되어 서비스 중단을 막음
    - 데이터 충돌 문제 X
    - 평소에는 비싼 서버 한 대를 놀려야 하므로 비용 낭비가 큼
- 하나의 DB 서버가 죽어버려도, 묶여있는 다른 서버가 즉시 역할을 이어받아 서비스 중단 없는 높은 가용성을 보장
    - 스토리지는 하나를 공유하는 경우가 많음

> 클러스터링 환경에서 Active 서버가 죽어서 Standby 서버로 Fail-over 되었습니다. 완벽하게 무장애를 보장하나요?
> 
- DB 서버 단의 장애는 막을 수 있지만, 치명적 단점 존재함
- 두 서버가 **하나의 스토리지를 공유하기 때문에, 만약 스토리지 자체가 물리적으로 고장나면 클러스터링 전체가 마비**되는 단일 장애점(SPOF, Single Point of Failure) 문제가 존재

### 실제 대규모 트래픽을 감당하는 서비스나 금융 시스템에서는 클러스터링, 레플리케이션 취합하여 섞어 사용

- 메인 DB 센터는 **클러스터링(Active-Standby)**으로 구성하여 서버 장애에 대비
- 다른 물리적 지역(재해복구 센터 등)에 **레플리케이션(Slave)**로 데이터를 복제해 두어 읽기 부하를 분산시키고 스토리지 장애까지 대비

## 수직 파티셔닝 vs 샤딩(수평 파티셔닝)

### 수직 파티셔닝

- 테이블의 Column을 기준으로 쪼갬
- 게시판 테이블에서 자주 조회되는 제목, 작성자 컬럼과 아주 가끔 조회되는데 용량은 엄청 큰 본문(TEXT/BLOB) 컬럼 분리
    
    ⇒ 자주 쓰는 데이터만 메모리(버퍼 풀)에 들어가서 캐시 효율 극대화
    

### 수평 파티셔닝 & 샤딩

- 테이블의 Row를 기준으로 물리적으로 서로 다른 DB 서버에 쪼개어 담음

> **Shard Key는 어떻게 설정할 건가요?**
> 
- Range 방식
    - 가입일자 기준으로..
- Hash 방식
    - 유저 ID를 해시 함수에 돌려서 나머지 값에 따라 DB를 균등하게 배분하는 방식
    - 트래픽이 골고루 분산
    - DB 서버를 한대 더 추가하려고 하면, 해시로직이 바뀌면서 기존 데이터를 전부 재배치해야 함
        
        ⇒ 안정 해시(Consistent Hashing)
        
        - Consistent Hashing
            - 데이터를 해시링(Ring) 위에 배치하고 서버를 추가/삭제할 때 전체 데이터가 아닌 인접한 서버의 일부 데이터만 재배치하도록 만들어, 확장 시 발생하는 부하를 획기적으로 줄임
            

> **샤딩의 단점을 어떻게 극복하나요?**
> 
- 서로 다른 DB서버에 데이터가 찢어져있기 때문에 Cross-Shard JOIN(서버 간 조인)이 불가능
- DB 단의 조인을 포기하고 애플리케이션(코드) 레벨에서 데이터를 각각 가져와 조합하거나
- 애초에 조인이 필요없도록 테이블을 **반정규화하여 중복 데이터를 허용하는 방식으로 아키텍처 설계**

## Statement vs PreparedStatement & SQL Injection

### SQL Injection (SQL 주입 공격)

- 해커가 입력창에 악의적인 문자열을 넣어, 백엔드의 쿼리 구조 자체를 파괴하고 무단으로 로그인하거나 데이터를 삭제하는 치명적인 보안 취약점

### Statement

- 쿼리와 사용자의 입력값을 **단순 문자열 더하기(+)**로 합쳐져서 DB로 보냄
    - `SELECT * FROM users WHERE id = ‘” + userInput + “’”`
    - 합쳐진 문자열을 그대로 컴파일하고 실행하기 때문에 SQL Injection에 100% 무방비로 당하게 됨

### PreparedStatement

- 쿼리의 틀을 먼저 DB에 보내서 미리 컴파일 시킴
    - `SELECT * FROM users WHERE id = “?”`
    - 그후, ? 자리에 사용자 입력값을 바인딩하여 보냄
- 방어 원리
    - DB는 이미 쿼리 구조를 분석 완료했기 때문에, 나중에 들어오는 입력값은 절대 실행 가능한 SQL 명령어로 인식하지 않고 순수한 데이터(String)로만 취급
    - SQL Injection을 원천 차단하는 가장 확실한 방법
    - 미리 컴파일해 두기 때문에 반복 실행 시 성능도 훨씬 좋음

> **테이블에 데이터가 1억 건이 넘어가서 느려지는데 어떻게 할까요?**
> 
1. 인덱스 최적화 및 실행 계획 분석: 인덱스가 꼬였는지, 풀 스캔이 도는지 먼저 확인
2. 커버링 인덱스 활용: 실제 데이터 블록까지 가지 않고 인덱스만으로 응답을 주도록 쿼리를 튜닝
3. 파티셔닝/아카이빙: 최근 1년 치 데이터만 남기고, 과거 데이터는 History 전용 테이블로 올김
4. 반정규화 및 집계 테이블 구축: 매출 1억건을 SUM()하는 대신, 야간 배치(Batch)로 일별/월별 통계 테이블을 미리 만듦

> **쿼리 튜닝 관점에서는?**
> 
- 게시판 등에서 1억건의 데이터를 조회할 때 `LIMIT 1000000, 20` (오프셋 기반) 방식을 쓰면, 앞의 100만 건을 다 읽고 버려야 해서 DB 부하
- 대신 `WHERE id > 1000000 LIMIT 20` (커서 기반, No-Offset) 방식을 사용하면 인덱스를 타고 해당 위치로 바로 점프하므로 1억 건이라도 0.1초만에 조회 가능

## Redis vs Memcached (In-Memory Cache)

RAM에 데이터를 저장하여 디스크 I/O없이 초고속으로 데이터를 응답하는 캐시 시스템

### Memcached

- 구조가 단순하고 멀티스레드를 지원
- 오직 Key-Value 형태만 저장 가능
- 서버가 꺼지면 데이터가 모두 날아감

### Redis

- 싱글 스레드 기반이라 동시성 이슈 피하기 쉬움
- 강력한 자료구조 지원
    - 단순 문자열뿐만 아니라 List, Set, Hash, Sorted Set(ZSet) 등을 지원
        
        ⇒ 실시간 랭킹보드, 대기열 시스템 등을 구현할 때 최적의 선택
        
- 영속성(Persistence)
    - 메모리 데이터지만 디스크에 스냅샷(RDB)이나 로그(AOF)를 남겨, 서버가 재부팅되어도 데이터를 복구할 수 있는 기능
- Cache-Aside

    1. Look In Cache (캐시 먼저)
        - 클라이언트가 서버로 데이터 요청
        - 서버는 무겁고 느린 SQL DB로 바로 달려가지 않고, 제일 먼저 Redis 확인
        - Cache hit: 데이터 반환
            
            ⇒ 디스크 I/O 없이 메모리에서 바로 ⇒ 속도 빠름
            
    2. Cache Miss > Look In Persistent Datastore
        - Cache miss: 만약 Redis를 뒤졌는데 찾는 데이터가 없음
            - 처음 요청하거나, TTL이 지나서 지워짐
        - SQL Database로 가서 쿼리 날림
    3. Prime Cache With Data
        - DB에서 가져온 데이터를 클라이언트에게 반환해주면서
        - 동시에 다음번 요청을 위해 Redis에 Prime(저장)
- Redis Replication

    - Master
        - 쓰기 작업 전담
        - 캐시에 새로운 데이터를 넣거나 수정
    - Replica 1, Replica 2
        - Master에 들어온 데이터를 실시가능로 복사(동기화)해서 똑같이 가짐
        - 읽기 전용

        - Reids Sentinel: 승격 작업을 자동으로 해줌

> **왜 Memcached 대신 Redis?**
> 
- 단순 Key-Value만 지원하는 Memcached와 달리, Redis는 List, Hash, Sorted Set(Zset) 같은 자료구조를 지원
- 대규모 콘서트 티켓팅의 ‘대기열 순번표’나 ‘실시간 랭킹보드’를 RDBMS로 구현하면 DB가 바로 터지지만
- Redis의 Sorted Set을 쓰면 O(log N) 속도로 가볍게 처리 가능
- 싱글 스레드
    - 한번에 하나의 명령어만 처리하기 때문에, 여러 스레드가 동시에 같은 데이터를 수정하려고 할 때 발생하는 동시성 문제를 쉽게 피할 수 있음
    - ex) 쿠폰 100장 선착순 발급 로직

> **캐시 스탬피드(Cache Stampede) 현상이란?**
> 
- 이벤트 배너 데이터처럼 엄청나게 많은 유저가 동시에 조회하는 캐시 데이터가 있을 때
- 이 캐시의 만료 시간(TTL)이 딱 끝나는 0.1초의 순간, 수만명 요청이 캐시를 뚫고 그대로 밑단에 있는 원본 DB로 쏟아져 들어가는 현상
1. **분산 락(Distributed Lock)**
    
    캐시가 만료되었을 때, 수만 개의 요청 중 딱 하나의 스레드만 락(Lock)을 획득해서 DB에 다녀오게 하고,
    
    나머지 요청들은 잠깐 대기시켰다가 갱신된 캐시를 읽게 만드는 방법
    
    Redis의 SETNX 명령어 활용
    
2. **논리적 만료 (PER: Probabilistic Early Recomputation)**
    
    실제 캐시가 날아가기 전에, 백그라운드 스레드가 미리 알아서 DB를 조회해 캐시를 최신화해 두는 방식
    

> **Redis의 RAM 용량은 무한하지 않은데, 꽉차면 어떻게 되나요?**
> 
- 메모리가 꽉 찼을 때 어떤 데이터를 지울지 결정하는 Eviction Policy(퇴출 정책) 설정
- 가장 오랫동안 쓰지 않은 데이터를 지우는 LRU, 가장 적게 조회된 데이터를 지우는 LFU 정책을 주로 사용

## Elastic Search

- RDBMS의 검색 한계를 돌파하기 위한 분산 검색 엔진
    - 김채현"이 포함된 모든 글을 찾을 때, `LIKE '%채현%'`을 사용하면 B-Tree 인덱스를 탈 수 없어 1억 건의 데이터를 처음부터 끝까지 다 뒤지는 Full Table Scan이 발생
- 역인덱스
    - 책 맨 뒤의 색인 페이지처럼, “단어 → 핵심 단어가 포함된 문서 번호” 형태로 데이터를 쪼개어 저장
    - ‘프론트엔드’라는 단어를 검색하면 전체 문서를 뒤질 필요 없이, 역인덱스 사전에서 ‘프론트엔드’를 찾아 거기에 적힌 문서 번호들만 바로 가져오므로 검색 속도가 빠름
- 쇼핑몰 상품 검색, 대규모 자동완성, 복잡한 필터링이 들어간 Dynamic query
